# 世界模型设计（位置图 · 事实库 2.0 · 信念层）

> 状态：设计定稿（2026-10）。本文描述逻辑结构，不含实现代码。
> 本文合并两项设计：探索系统（位置图 / 进场描述 / 动态生成）与事实库 2.0（作用域 / 两层事实模型 / 信念层）。
> 前置阅读：`docs/narration_design.md`（旁白系统与 2026-10 裁剪记录）、`docs/architecture.md`（五家族命名与现有调用链）。
> 本设计建立在旁白系统之上；与 2026-10 裁剪的关系见 §12——位置层是**结构层**，不是数据桥。

## 0. 已拍板决策（置顶）

| # | 议题 | 决策 |
|---|---|---|
| D1 | 地图 UI | **暂不做界面**，测试阶段手动选择地点；但**图状数据结构先行保留**（节点/边/当前位置） |
| D2 | 两层事实模型 | **接受**：正典只存客观世界事实；NPC 的主观认知（谎言/印象/私事）留在各自信念层 |
| D3 | 对话的写入边界 | **对话只修改某 NPC 的知识库与记忆，绝对不影响事实库**——旁白写正典、对话写日志，两条单向写入硬线 |

| D5 | 旁白注入 | **不再全量注入正典**：按当前地点作用域优先，再按上下文补充相关作用域与全局提要 |

## 1. 总览：三层世界数据与两条写入硬线

```
                    ┌─────────────────────────────────────────────┐
                    │  EntityRegistry 实体注册表（§3）              │
                    │  person / location / faction 实体 + 别名      │
                    │  作者导入 + 动态生成 + 玩家实体                │
                    └──────┬──────────────────┬───────────────────┘
                           │ 提供作用域的"挂靠点" │
        ┌──────────────────▼───┐      ┌────────▼─────────────────┐
        │ LocationStore 位置图  │      │ CanonStore 2.0 世界事实库 │
        │ 节点/边/当前位置       │      │ 条目 + 作用域标签表        │
        │ （结构层，引擎读写）    │      │ （客观世界事实）           │
        └──────────────────┬───┘      └───────▲──────────────────┘
                           │                  │ ③检索（评分，只读）
              ②进场描述/事实挂接│                  │
        ┌──────────────────▼───┐      ┌────────┴─────────────────┐
        │ NarrationController   │      │ NPC 信念层（知识日志演进）  │
        │ 旁白域：写正典【硬线①】│      │ 信念引用 + 主观条目 + 记忆  │
        └──────────────────┬───┘      │ DialogueController 写【硬线②】
                           │          └──────────────────────────┘
                    探索屏（叙述/移动/进场）      对话屏（与在场 NPC 对话）
```

**两条写入硬线（D3，全系统最高优先级约束）：**

- **硬线①**：旁白回合是事实库的**唯一写入者**（facts 落地）。旁白不读、不写任何 NPC 的信念层。
- **硬线②**：对话只写**该 NPC 自己的**知识库（信念）与记忆。对话的任何产物——学习、谎言、好感——绝不进入事实库。

由此，两个系统的关系被定义为：**旁白写世界，NPC 通过信念层"阅读"世界**。玩家对 NPC 说了什么，不会改变世界事实；但会被那个 NPC 记在信念里——世界不变，人心会变。

## 2. 实体注册表（EntityRegistry）

作用域的"挂靠点"。一切可被事实关联的东西都必须在注册表里。

### 2.1 条目结构

```
{ entity_id, type, canonical_name, aliases[], source, status }
```

| 字段 | 说明 |
|---|---|
| `type` | `person`（NPC 与玩家）/ `location`（地点）/ `faction`（组织）；可扩展 |
| `canonical_name` | 规范名（材料包注入的闭集命名清单用此名） |
| `aliases` | 别名表（"沈掌柜"→shen_moyan；"茶馆"→teahouse）。作者卡可声明，生成时登记 |
| `source` | `author`（作者数据导入）/ `gen`（游玩中动态生成） |
| `status` | `active`（当前唯一取值；预留扩展位） |

### 2.2 导入与生成

- **作者导入**：`characters/*.json` → person 实体（id = 卡 id）；`scenes/*.json` → location 实体（id = 场景 id）；`factions.json` → faction 实体。作者实体是**锚**：不可被生成物覆盖。
- **玩家**：固定 person 实体 `id="player"`（D4）。玩家无知识库、无记忆、无对话——它存在的意义是让"关于玩家的公开事实"有处可挂（§5）。
- **动态生成**：探索回合的 discoveries（§3.6）→ `gen_` 前缀 id，进注册表、进人物页（若为 person）。

## 3. 位置图（LocationStore）与探索流程

### 3.1 数据结构（D1：先留结构，不做图 UI）

```
{ locations: [{ entity_id, brief, source, status }],     // brief = 冻结的进场描述
  edges: [{a, b}],                                       // 已知可达路线（无向）
  current: entity_id }                                   // 玩家当前位置
```

持久化 `saves/world/locations.json`。作者场景卡导入为初始节点；初始路线由场景卡的 `links` 字段声明（作者写邻接），未声明 links 的作者场景默认全部连通到第一个场景（兜底，防死锁——跑团规范"至少留一条无条件的出口"的同款自觉）。

### 3.2 移动（无 LLM）

地点屏点相邻地点 → `cmd_travel_to(entity_id)` → 引擎校验有边 → 更新 current → 广播。移动零模型参与；不相邻的地点不可点（"你还没找到去那里的路"）。

### 3.3 进场描述（首次生成、正典冻结）

首次进入某地点：组装**进场包**（作者场景卡素材 + 该地作用域正典事实 + 近期流水）→ 一次生成到达描述 → **冻结为该地点的 brief**。再次进入：直接显示 brief + 引擎拼的回归行（"你再次回到顺水居的大堂。"），零延迟零调用。地点观感随剧情变化走正典取代通道（"茶馆今日歇业"取代旧观感），不重新生成——同一酒馆两次进门不能长得不一样。

### 3.4 地点屏（探索屏升级）

现有探索屏增加两个区块：**位置面板**（当前位置 + 相邻地点移动按钮）与**在场 NPC 列表**（见 §3.5）。叙述流、行动输入、调试侧栏不变。测试阶段（D1）无图 UI，位置面板即移动入口。

### 3.5 在场 NPC 与对话入口

地点持有 NPC id 列表：作者 NPC 由场景卡 `npcs` 字段声明；生成 NPC 在诞生时落位。地点屏列出在场 NPC，点击 → 既有 `dialogue_requested` → 对话屏预选并开始。**对话系统零改动**——它不知道位置的存在，只是入口被"谁在这里"过滤。这不是数据桥：没有数据流过，只有人站在这头。

### 3.6 动态生成（discoveries）与护栏

旁白输出契约新增可选块：

```
discoveries: { locations: [{name, brief}], npcs: [{name, identity, brief}] }
```

模型只提名与简介；**连线、去重、落位、建卡全是引擎的事**（受控开放）。落地规则：

- 每回合 locations、npcs 各限 1 个；名称与注册表精确去重（同名视为同一实体）；
- 长度截断：名称 ≤12 字、brief ≤100 字；
- 新地点：注册表注册 → 位置图建节点 → 与当前位置连边 → 首次进场时再生成完整描述（brief 先用模型给的）；
- 新 NPC：注册表注册 → **自动生成人物卡**（SnapshotStore persona 区，id=`gen_` 前缀）→ 落位当前地点 → 进人物总览页，玩家可编辑其人设与好感度（复用现成基建）；
- 来源标记：玩家明确发起的发明的实体标 player 来源（半采纳原则同正典）；
- 作者实体是锚：生成物不得覆盖任何作者实体的字段。

## 4. 世界事实库 2.0（CanonStore 演进）

### 4.1 条目结构

```
{ id, content, source(narrator|player), weight(major|minor),
  status(active|superseded), superseded_by, created_at,
  scope: [{type, entity_id}] }        ← 新增：作用域标签表
```

- **作用域是标签表，不是四选一枚举**：一条事实可同时挂 `[{location, teahouse}, {person, shen_moyan}]`。将来扩展 item/event 作用域零迁移。
- **scope 为空 = 全局**（默认态）。全局不是桶，是"尚未归属或本就全局"的天然态。
- **玩家可作 scope**：`[{person, player}]`——玩家的行迹与公开名声（"此人在茶馆当众质问税官"）挂玩家作用域，这是其他 NPC 认知玩家的客观依据（D4）。
- 迁移：现有 canon.json 条目无 scope → 默认空（全局），不迁移数据。

### 4.2 什么能进正典（事实纪律第四条）

正典只收**客观的、第三人称可验证的陈述**。既有三条铁律不变（不违背世界观/取代通道/依赖性细节显式入库），新增第四条：

> **4. 不记任何人的内心。** NPC 的态度、情感、对玩家的看法属于该 NPC 的信念层（对话域），不是世界事实。"守林人警告过狼群"可入正典（可观察的行为），"守林人对玩家产生好感"不可（主观）。

这条与硬线②呼应：内心状态只由对话域在信念层里维护。

### 4.3 supersede 涟漪与按作用域配额

- 取代机制不变（只标不删）。新增涟漪语义：正典条目被取代时，**引用它的信念自动标记 stale**（见 §5.3）——NPC 可以继续坚信旧版本，直到被再次说服。消息传得慢，是真实感的来源。
- 预算压缩改为**按作用域分别配额**（每个地点作用域独立预算，如各 40 条；全局提要独立预算），取代现在一刀切的 120 条。

## 5. NPC 信念层（知识日志演进）

### 5.1 两种条目

NPC 的知识日志（KnowledgeJournal 演进）持有两类条目：

| 条目 | 形态 | 例子 |
|---|---|---|
| **信念引用** | `{fact_id, trust, learned_at, evidence}` | 指向正典条目 + 自己的信任档 + 亲历证据。玩家说的话经佐证/矛盾算术升降这个 trust |
| **主观条目** | 现有 learned 条目形态（content/evidence/speaker/trust） | 谎言、印象、私事、"这人昨天来问过仓库"——不进正典的东西 |

信任算术（佐证 +1 / 矛盾 -1 / 复活 / 玩家永不直接产生绝对可信）**全部作用在信念上**，语义不变——变的只是：当所学内容实为客观世界事实时，日志里存"引用"而不是"复制品"。

### 5.2 记忆与知识分离

- **记忆（memory）**：NPC 的第一人称亲历叙事（"今天来了个生面孔，问起拳手的事"）。对话结算生成，只属于这个 NPC。
- **知识（信念）**：对世界的认知（引用 + 主观条目），带来源与信任。
两者在日志里分区存放，材料包分区注入——回到原设计 4.10 的本意。

### 5.3 过时语义（stale）

正典条目被 supersede 时，引用它的信念标记 `stale`（不删除、不改信任）。对话材料包渲染时给 stale 信念加"（听说的事似乎有变）"标注——NPC 可以继续坚信旧版本，这正是"消息传得慢"的真实感来源。玩家说服 NPC 接受新事实 = 一次佐证（trust 提升 + stale 清除）。

### 5.4 硬线②的执行点

对话结算（MemorySummarizer → 学习路径）是信念层的唯一写入者；写的是**日志**，不是正典。学习路径的实体消解：某条 learned 内容经引擎评分匹配到正典条目 → 记信念引用；匹配不到 → 主观条目（现状形态）。**没有任何路径从对话域写 CanonStore。**

## 6. 检索与注入配方

### 6.1 检索：确定性评分优先

检索 = "谁可能知道哪些世界事实"。**引擎评分为主，完全确定性**：

```
得分 = 作用域命中（地点相同 / 实体相同 / 组织相同）× 权重（major>minor）× 新近度
```

玩家与 NPC 的"在场历史"以**地点作用域**为代理（NPC 驻扎在某地 = 他听得进本地新闻；玩家去过某地 = 他亲历了那里的公开事实）。语义级检索（agent/RAG）**降级为可选增强件**，评分不足时才启用，且默认关闭——以我们的数据规模（数百条中文短句 + 注册表精确匹配），确定性检索覆盖绝大多数场景。这与"引擎定事实"哲学一致：认知的正确性不交给一次概率调用。

### 6.2 旁白材料包配方（替换全量注入）

```
① 当前地点作用域：全量（本地戏份为主）
② 全局 major 提要：每条一行，上限 15 条（大事件跨越地理边界）
③ 本回合被提及实体的作用域：注册表命中的实体名下事实
④ 近期流水 + 玩家行动原文（不变）
⑤ 实体注册表规范名清单（当前地点 / 在场 NPC / 组织 / 全局 major 涉及实体）——实体命名的闭集
```

### 6.3 对话材料包配方

NPC 的材料 = **信念层全量**（含 stale 标注与主观条目）+ **检索到的可信世界事实**（NPC 所在地点作用域 + 全局 major 提要，评分过滤）。原"知识日志全量注入"的膨胀问题随作用域化一并解决。

## 9. 迁移与兼容

- canon.json 旧条目：无 scope → 默认全局；不迁移。

- 人物卡：无需新字段（在场由场景卡声明，单一来源）。

## 12. 与 2026-10 裁剪的关系

裁剪确立的"旁白与对话相互独立"在本设计中**升级为两条单向写入硬线**（§1），而非恢复数据桥：

- 位置层是**结构层**：地点与在场是"世界的骨架"，两系统都读它，但没有任何叙述/事实/信念数据流过它；
- 对话域从正典**只读**（评分检索），旁白域对日志**不读不写**；
- 若将来要重接数据级桥（如对话产物影响世界事实），仍按 `narration_design.md` 变更记录的恢复点清单操作，且必须以显式机制（如 author 触发器）越过硬线②，不允许隐式写入。
