# 动态生成系统设计方案（地点 / 人物 / 组织）v2

> 状态：**已实施**（一期+二期核心落地；实现类清单见文末与 docs/code_reading_guide.md §5）。
> 离线端到端测试：`godot --headless -s tests/gen_loop_test.gd`。
> 功能：玩家在游玩中可能"发现"世界里原本不存在的新地点、新人物、新组织。
> 由 DM 判断要不要生成，然后交给三个专门的生成 agent（每个类型一个）去编写内容。
> **所有生成内容只写入 saves/（运行期数据目录），settings/（作者设定目录）一个字节都不动。**
>
> 设计原则（按优先级）：
> 1. **逻辑一致性最重要**：生成的知识、记忆必须符合这个身份"应该知道什么"。
>    铜锈区的炉工不知道天穹台的机密；做不到就宁可少生成，不能生成穿帮的内容。
> 2. **时间成本次之**：生成一个新东西可以接受多次大模型调用（比如"先写草稿、
>    再检查、再修改"的多轮流程），游戏里等一两分钟是可以忍受的。

---

## 0. 先看这里：名词解释

本文档会反复用到这几个词，先说清楚：

| 名词 | 意思 |
|---|---|
| **正典** | 全世界的客观事实清单（`CanonStore`）。比如"作坊市街的EI屏上个月跌破过警戒线"。所有叙述都不能和它矛盾。 |
| **事实的可见性（visibility）** | 一条事实"谁能知道"，分四档（见 §5）。 |
| **候选知识池** | 生成一个新人物时，引擎先算好"以他的身份，他允许知道哪些事实"，做成一张带编号的清单。生成 agent 只能从这张清单里引用，引用清单外的编号会被引擎直接丢弃。 |
| **知情集** | 一个新人物"可能认识、可能听说过"的人和势力的集合：同一地点的邻居、同一组织的同事、设定里明确认识的人。 |
| **闭集校验** | 模型只能从引擎给的编号清单里选；选了清单外的东西，引擎直接丢弃并记一条说明，不报错。这是全项目防模型胡说的基本手段。 |
| **gen_ 前缀** | 动态生成的实体的 id 都带 `gen_` 前缀（如 `gen_3`），和作者手写的实体永远分得清。 |
| **落地** | 内容校验通过后，真正写进游戏数据（注册表、正典、快照文件）的动作。 |

## 1. 触发：DM 什么时候发起生成

DM 在裁决玩家输入时，如果发现玩家的行为指向一个**世界里还没写过**的东西
（敲开一扇从没开过的门、打听一个没出场的人、卷入一个没提过的势力），
就调用新工具 `world.discover`：

```json
{"tool": "world.discover",
 "args": {"kind": "location / character / faction 三选一",
          "brief": "一句话说明要生成什么，60 字以内"}}
```

约束（引擎强制，不靠模型自觉）：

- `kind` 只能是三个值之一，其他值丢弃；
- 每段探索最多发起 **3 次**生成，超出的丢弃并记录原因（防止玩家刷出满城新铺子）；
- `brief` 超 60 字截断；
- 生成期间玩家不能行动（见 §3 第 6 步）。

---

## 2. 总流程（一步一步）

1. 玩家输入，DM 正常裁决（现状不变）。
2. DM 决定"这里应该长出新东西"，输出 `world.discover` 工具调用。
3. DMController 把请求转交给 **GenController**（新的控制器，三个生成 agent
   的宿主）。DM 的工作到此结束，不再参与生成。
4. GenController **冻结生成上下文**：这一步很关键——生成时参考的所有材料
   （世界观、相关正典、候选知识池、知情集、现存名字清单）在生成开始前定死，
   生成过程中不因任何原因改变。
5. 按 kind 走对应管线，跑"构思 → 审核 → 修订"多轮循环（见 §4）。
6. 生成期间玩家输入被挡住，界面显示当前阶段（"构思中 → 一致性审核中 →
   修订中"）。完整生成约 1–3 分钟（见 §4 的调用预算）。
7. 校验全部通过 → 落地（写入 saves/ 下的各数据文件）→ 自动往正典里加一条
   "存在事实"（见 §6.1）→ 界面出现系统提示（"你注意到……"）。
8. 校验在预算内始终不通过 → 放弃生成，世界没有任何变化，界面提示"你似乎
   注意到了什么，但没放在心上"。**宁可少生成，不能生成穿帮的内容。**

三种生成**互相独立、可以单独发生**（见 §5）：
生成新地点不要求同时生成里面的人；生成人物不要求他有组织；生成组织不要求
成员里有能对话的人物。彼此关联（比如"新铺子和它的掌柜"）只在 DM 的 brief
明确说了要关联时才链式生成。

## 3. 多轮生成管线：构思 → 审核 → 修订

每一轮生成不是一个调用完成，而是最多三轮大模型调用，用时间换质量：

| 阶段 | 调用什么 | 做什么 |
|---|---|---|
| **构思** | 该类型的生成 agent（`PURPOSE_GEN_LOCATION / _CHARACTER / _FACTION`） | 根据冻结的上下文写出完整草稿 |
| **审核** | 独立的**审核者 agent**（`PURPOSE_GEN_AUDIT`，三种类型共用） | 站在"世界一致性检查员"的角度挑毛病，输出 `{verdict: pass / revise, issues: [每条问题]}` |
| **修订** | 该类型的生成 agent（带着草稿和问题清单再写一遍） | 只针对问题清单修改，重新输出完整内容 |

审核者的检查清单（写死在它的提示词里，按类型裁剪）：

1. **信息越权**：这个人物知道的事，超出他身份该知道的范围了吗？
   （炉工的口吻像不像听过天穹台的内幕？）
2. **世界观冲突**：草稿和正典、世界观文本有矛盾吗？
3. **风格错位**：用语质感和他所在的环区匹配吗？（渊薮的乞丐不该说白银廊的腔调。）
4. **重复**：和现存的角色/地点只是换了个名字吗？
5. **互相引用对不上**：地点和住户、组织和成员之间的指涉关系自洽吗？

循环规则：

- 审核 `pass` → 通过；
- 审核 `revise` → 带着问题清单修订，修订稿再审核，**最多修订 2 轮**（可配置）；
- 每一轮之间，引擎的**闭集校验照常执行**。审核者负责"确定性代码查不了的
  语义问题"；编号越界、名字撞车这类硬性错误由引擎直接拦截。两层各管各的。
- 预算内始终不通过 → 放弃（见 §2 第 8 步）。

调用预算（deepseek-flash，单次约 3–8 秒）：地点约 3–6 次调用、人物约 3–6 次、
组织约 2–4 次。世界屏状态栏分阶段显示进度，等待是可感知、有反馈的。

## 4. 三种生成各自做什么

三种生成完全独立。**单独生成就完全可用**：地点可以空无一人（一口封死的井、
一间锁着的仓库），人物可以没有归属地点（一个过路人），组织可以全是提不到
名字的配角。

### 4.1 新地点（可以没有任何人）

- **输入**：世界观、当前地点与相邻地点清单、当前地点的正典、近期流水、
  brief、现存地点名清单（防止撞名）。
- **输出**：`{name, aliases[], brief(进场描述，200字内), environment,
  atmosphere, opening_situation, facts: [0–3 条本地事实], inhabitants: [0–2 个住户简报]}`。
- `facts` 是这个地点的本地事实（比如"柜台下面有个暗格"），落地时写入正典、
  作用域挂在新地点名下——玩家走到这里时，DM 检索自然能看到。
- `inhabitants` 是**可选的**：只有 brief 明确说"这地方有人"才生成（比如
  "一家有掌柜的新铺子"）；默认为空。住户只是简报，人物细节由人物 agent
  生成（链式排队，先落地地点再生成住户，住户就能正确引用这个地点）。
- **落地**：注册 gen 实体（`gen_` id）→ 挂进位置图并与当前地点连边 →
  brief 直接冻结为进场描述（以后再进不重复生成）→ 有住户则排队人物生成。
- **持久化**：`saves/world/locations.json` + `saves/world/entities.json`。

### 4.2 新人物（知识按身份分层，见 §5）

- **输入**：世界观、所在地点的场景素材与本地正典、**候选知识池**（§5.2）、
  **知情集**、归属组织信息（若有）、现存人物名清单、一个同地点 NPC 的说话
  风格示例（供参考，不是照抄）。
- **输出**：`{name, aliases[], identity(40字内), profile(200字内，含说话风格),
  home, faction_ids[], knowledge: [...], memories: [最多3条], affinity}`。
- `knowledge`（初始知识）只有两种合法形态：
  - `{ref: 候选池编号}`——引用一条允许知道的正典事实；
  - `{content: 内容, basis: 来源说明}`——主观条目（亲历/听说），basis 必须
    注明来源属于哪一层。引擎会扫描 content 里提到的每个人物/组织名，
    **只要有一个人不在知情集里，整条丢弃**。
- `memories`：只能引用自己的知识和场景素材，最多 3 条、每条 60 字内。
  记忆是主观经历，做结构校验即可，不做事实核对。
- **落地**：构建人物模型 → 写 `saves/characters/gen_<id>.json`（和作者人物卡
  同款的双区快照，这是人物数据的唯一写入口）→ 广播"设定已变化"信号让其他
  域重载 → 放进 home 地点的在场名单。生成的人物此后和作者写的人物**完全
  同权**：可以对话、可以学习、可以长记忆。
- **持久化**：`saves/characters/gen_<id>.json` + `saves/world/entities.json`。

### 4.3 新组织

- **输入**：世界观、brief、现存组织名/人物名清单。
- **输出**：`{name, description(120字内), members: [{name, position} 最多6个]}`。
  members 可以引用现存人物（名字必须在现存人物或本批生成人物里），
  也可以是纯配角名（和作者写的组织一样，配角不需要有卡）。
- **落地**：写入 `saves/world/gen_factions.json`——这是动态组织的**唯一
  写入口**（新文件；因为现有的实体存档只保存公共字段，装不下组织介绍和
  成员表）。游戏加载时会自动合并这个文件，和作者的组织同等对待。
- **持久化**：`saves/world/gen_factions.json` + `saves/world/entities.json`。

## 5. 事实库：可见性分层与候选知识池

这是"小市民不知道高层秘密"的机械保证，分两小节。

### 5.1 给每条正典事实标注"谁能知道"

正典事实新增一个字段 **visibility（可见性）**，四档：

| 档 | 意思 | 例子 |
|---|---|---|
| LAW 人人皆知 | 世界法则，所有居民都知道 | 魔力法则、施法三大定律、七个环区 |
| PUBLIC 公共传闻 | 发生过、传开了的事 | 拳手死了、幕帘辟谣 |
| LOCAL 本地限定 | 只有相关范围的人知道 | 某地发生的事、某个NPC的身份 |
| SECRET 有限知情 | 知情人很少 | （目前正典里没有，留给未来） |

- **默认推导**：写入时不说就用范围推导——没有作用域（全局）→ PUBLIC，
  有作用域 → LOCAL。按此检验现有 53 条正典：渊薮的婆婆知道魔力法则和拳手案
  （默认 PUBLIC，正确——这些本来就是全城皆知），而那些真正的秘密（严知衡
  掌握的处理器的冗余度）从来不在正典里，是人物卡里的私有知识，生成 agent
  根本看不到。
- 作者可以在 `settings/canon.json` 里手动标注（建议把魔力法则、三大定律、
  七环区、慈母帷幔、汲取器、情绪税、晶石这几条标成 LAW）。
- 说明：visibility 目前**只影响生成时的候选知识池**（§5.2），不改变运行期的
  事实检索行为。

### 5.2 候选知识池：生成人物时"允许他知道的事"

生成人物前，引擎按三条规则确定性构建一张带编号的清单：

| 来源 | 规则 | 例子 |
|---|---|---|
| 人人皆知的 | visibility 是 LAW 或 PUBLIC 的正典 | 魔力法则、拳手案 |
| 本地的 | visibility 是 LOCAL，且作用域包含这个人物的家/所在地 | 百草堂的诊金规矩 |
| 圈子里的 | 作用域命中知情集里的实体（同组织同事、brief 指定的相识） | 组织内部的约定 |

清单之外的事实：**不注入给 agent、引用编号会被丢弃、内容里提到也会被丢弃**。
泄漏在物理上不可达——素材里根本没有，模型想编都不知道往哪个方向编。
就算模型硬编出"她其实是市长的私生女"这种内容，因为"市长"不在一个铜锈区
炉工的知情集里，这条知识整条丢弃，不会进入游戏。

## 6. 事实库的变化：新东西出现后，正典和旧事实怎么办

生成不只是"加一个实体"，还要处理好它和**既有事实库**的关系。三个动作：

### 6.1 自动写入"存在事实"

每个新实体落地时，引擎自动往正典加一条它的存在记录，例如：

> "作坊市街新开了一间符文铺，掌柜自称唐门之后"（作用域=[新地点, 新人物]，可见性=LOCAL）

这一步保证：**后续回合的 DM 检索能召回这个新实体**——没有这条，世界玩着
玩着就"忘记"它存在了。

### 6.2 旧事实被新实体推翻 → 走取代链

新东西的出现可能让某条旧事实不再成立。比如正典里有一条"这条巷子没有别的
出口"，而玩家刚刚让 DM 生成了"巷尾新开的铺子"。处理方式：

- 生成契约里有一个可选字段 `fact_updates`：agent 提出旧事实的更新提议
  `{ref: 旧事实编号, content: 新表述}`；
- 引擎做闭集校验（ref 必须是本轮注入给它的正典编号，防编造）后，走既有的
  **取代链**（supersede：旧事实标记被取代、指向新事实，不删除，保留审计线索），
  并广播"涟漪"——有多少人物的知识引用了旧事实；
- 这与探索结算时的"事实整理者"同权：生成 agent 和整理者都是**授权编写世界
  事实的角色**，DM 依然没有改写正典的权力（硬线不变）。

### 6.3 什么不进正典：私事留在人物身上

新人物的知识里那些私事（"她在黑潮带有个仇家"）**不会**自动写入正典——正典
只收"世界已公开、已发生"的客观事实。私事留在人物自己的知识日志里，等玩家
在对话中把它挖出来，再由结算时的整理者 agent 提取入典。这样正典始终保持
"客观、可验证"的性质。

---

## 7. 已有人物会怎么变：知识不自动改，靠对话自然学习

新人物/新地点出现后，**既有的 NPC 不会自动被写入"我知道了这件事"**。
人物知识日志只在它自己的对话结算时变化——这是项目的重要不变量，不为生成
功能开新口子。新实体的信息传达到既有 NPC，靠的是三层既有机制：

1. **材料层天然可见**：存在事实的作用域挂在发生地，同地点 NPC 的材料包
   "你知道的世界事实"一栏自动包含它。玩家问茶馆掌柜"巷尾新开的铺子你去过
   吗"，掌柜能自然接话——不需要掌柜的日志里有这条。
2. **对话学习是唯一入口**：NPC 若因此产生了持久的认知变化（比如对玩家刮目
   相看），走它自己的对话结算（belief.propose → 信任算术），和现有机制完全
   一样。
3. **旧事实被取代时，知道旧事实的人自动"听说过时版"**：既有机制——人物的
   信念引用指向的正典被取代后，材料包渲染时自动标注〔听说的事似乎有变〕。
   所以 §6.2 的取代会自然波及所有知道旧事实的 NPC，不需要额外处理。

一句话：**正典立即变，人物慢慢变（通过他们自己的对话）**——这正是世界的
自然传播方式。

## 8. 持久化与生命周期（全部在 saves/，settings/ 一个字节不动）

| 内容 | 写入文件（唯一入口） | 游戏重启后 |
|---|---|---|
| 生成的人物 | `saves/characters/gen_<id>.json` | 自动加载（加载器已存在，本功能启用它） |
| 生成的地点 | `saves/world/locations.json` + `entities.json` | 自动加载 |
| 生成的组织 | `saves/world/gen_factions.json`（新文件） | 加载时合并（新增逻辑） |
| 存在事实与取代链 | `saves/world/canon.json` | 自动加载 |

- 作者设定的锚语义不受影响：每次启动都会从 `settings/` 重建作者实体（幂等），
  生成实体走各自的 saves/ 路径保留。
- 清理入口：调试侧栏新增"清除动态生成内容"按钮（删 gen_ 快照、gen 节点、
  gen_factions.json、作用域指向 gen 实体的正典条目），与现有"一键重置事实库"
  并列、互不影响。
- AuthorTool 导出的是作者设定，不包含生成内容——作者数据和运行期世界严格
  分离（如果以后想"把玩出来的世界固化成新设定"，可以再加导出功能，不在本期）。
- 防膨胀：每个存档的 gen 实体软上限 50 个，超限后 `world.discover` 被拒绝
  并提示。

## 9. 与既有硬线的核对

| 硬线 | 本方案如何遵守 |
|---|---|
| DM 不读不写 NPC 信念 | DM 只发 `world.discover` 请求；人物知识的写入由 GenController 完成（性质上等同"作者在写卡"），DM 全程不接触信念数据 |
| 对话域对正典只读 | 不变；生成的正典条目和作者正典同库同检索 |
| 材料包冻结 | 生成上下文在请求发起时冻结（同一哲学）；生成期间玩家输入被挡住 |
| 闭集即安全 | 知识编号、实体提及、组织成员、目标地点、kind 枚举，全部闭集校验 |
| 一切修改必须落盘 | §8 的每个文件都是唯一写入口 |

## 10. 改动清单

**新增文件**：

- `Scripts/Gen/gen_controller.gd`——autoload "Gen"：三条管线的编排、多轮
  构思/审核/修订循环、阶段状态广播；

## 12. 可行性评估

**工程可行性：高。** 落地所需的引擎函数全部现成（gen 实体注册、位置图挂载、
在场安置、人物快照双区读写、gen 人物加载器），本功能是让这批预留代码正式
转正；触发端只是 Toolcall 系统里新增一个工具类；校验哲学（闭集 + notes 留痕 +
宁缺毋滥）与全项目一致。无新依赖、无数据库。

**模型可行性：中高，多轮管线显著降低风险，且失败模式温和。** 单次生成的
质量风险由"审核 → 修订"循环兜住：审核者是专门校准的第二个视角（相当于把
项目规划中的"事实审核"机制先用在了生成场景）。语义层问题（口吻错位、身份
越权）由审核者捕获，硬性越界由引擎闭集捕获，两层互补。**最坏结果是内容
贫瘠或放弃生成，绝不会是世界穿帮（越界内容落库）。** 审核者误报的代价只是
多一轮修订；漏报由引擎兜底。运行时延迟（完整生成 1–3 分钟）按既定原则接受，
分阶段进度提示让等待可感知。

**一致性风险的诚实清单**：

1. 候选知识池收得太紧 → 人物知识贫瘠、像纸片人。缓解：人人皆知层给足，
   主观条目（带 basis）允许承载生活纹理；
2. 链式生成的住户可能在修订后仍引用失败 → 只放弃该住户，地点保留；
3. 生成期间玩家输入被挡 1–3 分钟 → 原则明确接受，界面分阶段反馈；
4. 长期游玩实体无界增长 → 每存档软上限 50 个；
5. 审核者自身质量决定语义检查的上限 → 它的提示词是二期调优重点，
   且它只增不减（漏报由引擎硬门兜底）。

**建议分期**：

- 一期（基建）：visibility 字段、`world.discover` 工具、GenController（含多轮
  编排与阶段广播）、gen_faction_store、LoreRepository 合并、Mock 样本、
  gen_loop_test；
- 二期（质量）：三个生成 agent 与审核者的提示词打磨、真实 API 用例
  T21–T23、清除按钮 UI。

## 13. 一个完整的例子（把全流程串起来）

1. 玩家（在作坊市街）输入：`我敲了敲巷尾那扇从来没开过的木门`。
2. DM 裁决：route=action，叙述"门开了一条缝，一个沙哑的声音问你是谁"，
   同时判断这值得生成一个新人物，调用
   `world.discover {kind: "character", brief: "木门后独居的隐士，对外界警惕"}`。
3. GenController 冻结上下文：候选知识池 = 人人皆知的 9 条 + 作坊市街本地事实
   + 夜巡队相关 2 条（brief 暗示他与夜巡队旧识）；知情集 = 秦峙、关大河、玩家。
4. 人物 agent 构思草稿：隐士"贺松"，前白银廊符文匠，**知识**：魔力法则（ref）、
   情绪税（ref）、"白银廊的工坊把报废符文件运进铜锈区"（ref，本地传闻）+
   主观条目"秦峙当年救过他一命"（知情集内 ✓）。
5. 审核者：口吻匹配 ✓，但发现一条知识提到"天穹台的巡逻规律"——**信息越权**
   （天穹台不在知情集）。verdict=revise。
6. 修订：删掉越权条目，重新输出。二轮审核 pass。
7. 落地：`gen_1` 入注册表与位置图（place_npc 到作坊市街）、快照写入
   `saves/characters/gen_1.json`、存在事实入典（LOCAL，作坊市街）、
   广播设定变化。界面："你注意到——木门后住着一个叫贺松的隐士。"
8. 之后玩家可以和贺松对话（他和作者写的人物完全同权）；同地点的秦峙在
   材料层能看到"贺松"的存在事实；如果玩家把贺松的事告诉别人、别人信了，
   那个人的日志才会（通过它自己的结算）长出这条知识。
